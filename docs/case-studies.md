# 사례 분석 — 대형 소비자 플랫폼은 되는가 (네이버·유튜브·인스타그램)

짧은 답: **요청을 그대로 재현하는 방식(T0~T2)으로는 사실상 안 된다. 그리고 셋 다 약관이 자동화·스크래핑을
금지한다.** 이 문서는 왜 그런지, 대신 무엇을 써야 하는지를 적는다. 조사 기준 2026-09.

`any-api` 의 전제를 다시 보자. 사내 회계 SaaS 가 뚫렸던 건 그 서비스가 **우리 고객의 계정**이고,
봇 차단이 없었으며, 서명이 프런트 JS 안에 있었기 때문이다(T2). 대형 소비자 플랫폼은 이 세 조건이 전부 다르다.

## 한눈에

| 플랫폼 | 등급 | 재현이 막히는 이유 | 약관 | 공식 대안 |
|---|---|---|---|---|
| **Instagram (Meta)** | T3 | TLS 지문으로 `requests`/`httpx` 를 핸드셰이크 단계에서 봇으로 식별. `x-ig-app-id` + 로그인 세션 요구, 세션 TTL 짧음, headless 탐지로 Playwright 가 수백 요청 내 차단. 4중 안티어뷰즈 스택 | 허가 없는 스크래핑·로그인 담장 뒤 콘텐츠 수집 금지 | **Instagram Graph API** (비즈니스·크리에이터 계정, Meta 앱 심사) |
| **YouTube (Google)** | T3 | 내부 API(InnerTube)가 **BotGuard attestation + PoToken** 을 요구. PoToken 은 visitorData/세션에 묶이고 브라우저에서 챌린지를 풀어야 생성됨. 서버에서 순수 재현 불가 | 자동 접근·다운로드 금지 | **YouTube Data API v3** (OAuth, 쿼터제) |
| **Naver** | T3 (서비스마다) | 로그인에 CAPTCHA·기기 검사. **2026-09-07 개정 약관**이 크롤러·봇·스크립트 자동 수집과 차단 우회를 명시적으로 금지 | 자동 수집·차단 우회 금지 | **Naver Developers 오픈 API** (검색·로그인 OAuth·지도 등) |

## 왜 사다리의 위쪽이 막히나

`any-api` 의 난이도 질문(`any-api.md` §3)에 대입하면 셋 다 Q4 = 예, 즉 **T3** 다.

- **TLS/기기 지문.** Instagram 은 HTTP 헤더를 보내기도 전에 TLS 핸드셰이크 모양으로 자동화 클라이언트를
  걸러낸다. `http-replay`(2단계 analyze 가 잡는 동적 헤더 재현)로는 이 계층을 통과하지 못한다.
- **브라우저 attestation.** YouTube 의 PoToken 은 "이 요청이 진짜 브라우저에서 왔다"를 증명하는
  챌린지를 브라우저가 풀어야 나온다. 서명 함수를 포팅하는 sign-hunt(3단계)로 될 일이 아니라,
  챌린지 실행 자체가 브라우저(또는 그걸 흉내 낸 전용 런타임)를 요구한다.
- **headless 탐지 + 세션 단명.** 설령 브라우저 안에서 호출해도(`browser-fetch`) headless 지표와 행동
  분석으로 수백 요청 안에 차단되고 세션이 만료된다.

## 사다리를 내려가면?

`any-api` 의 설계대로라면 T3 는 `browser-fetch` → `ui-automation` → `agent` 로 강등된다.
기술적으로는 **사람이 쓰는 실제 브라우저에서 천천히 조작**하는 `ui-automation`/`agent` 가 동작할 수
있다. 그러나 **여기서 멈춰야 하는 이유는 기술이 아니라 약관이다.**

- 셋 다 약관이 자동 수집을 금지한다. 프로젝트 원칙(`any-api.md` §6)은 "약관·계약상 허용된 서비스에만" 이고
  "차단 우회 금지" 다. headless 탐지를 피하려고 지문을 위조하거나 프록시를 돌리는 것은 **우회**이며
  이 프로젝트가 하지 않기로 한 것이다.
- 따라서 네이버·유튜브·인스타그램은 `any-api` 파이프라인에 **올리지 않는다.** 0단계(승인) 게이트에서
  "불가"로 분류된다.

## 그럼 무엇을 쓰나 — 공식 API

이 세 곳은 비공식 재현이 필요 없다. 공식 API 가 있고, `any-api` 는 그것을 **레시피로 감싸기만** 하면 된다
(`http-replay` 의 가장 쉬운 경우 — 서명도 봇 차단도 없이 발급된 토큰만 쓰면 됨).

| 원하는 것 | 공식 경로 |
|---|---|
| 인스타그램 비즈니스 계정의 미디어·인사이트 | Instagram Graph API (Meta 앱 등록·심사·권한) |
| 유튜브 영상·채널·검색·자막 메타 | YouTube Data API v3 (Google Cloud 프로젝트·OAuth·쿼터) |
| 네이버 검색·블로그·지도·로그인 | Naver Developers 오픈 API (애플리케이션 등록·클라이언트 ID/시크릿) |

공식 API 는 쿼터·권한·심사라는 제약이 있지만, 계정 정지나 약관 위반 없이 **지속 가능**하다.
`any-api` 의 가치는 여기서도 유효하다: 공식 API 마다 인증·페이지네이션·완전성 규칙을 레시피로 표준화해
다른 내부 비공식 레시피와 **같은 `runRecipe` 계약**으로 노출하는 것.

## 결론 — "아무거나 API" 의 정확한 범위

- **기술적으로** 재현 가능한 것은 봇 차단이 약하거나 없는 서비스(대개 사내/B2B/기관 시스템)다.
  대형 소비자 플랫폼은 T3 라 재현이 막히고, 막힌 것을 뚫는 것은 우회이므로 하지 않는다.
- **"무엇이든 하나의 API 계약으로"** 는 여전히 유효하다. 그 서비스가 공식 API 를 주면 그걸 레시피로 감싸고,
  비공식이지만 허용·미보호면 재현하며, 둘 다 아니면 사람(`human`) 단으로 내려간다. 셋 다 **같은 결과 형태**다.
- 한 줄로: **any-api 는 "차단을 뚫는 도구"가 아니라 "허용된 원천을 하나의 계약으로 통일하는 도구"다.**
